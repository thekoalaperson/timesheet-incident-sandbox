Run the incident scenarios

  1. Reset the demo before each scenario. Reset clears demo employees, time entries, and monitor observations.
  2. Run the baseline to confirm an 8-hour total and an OK monitor.
  3. Reset again, then run a bug scenario. Inspect the timesheet, monitor, alerts, and logs.
  4. Use log evidence to trace the issue to the service source.

Alerts reflect a rolling 60-second observation window. Service health retains an incident until reset. A cleared monitor does not necessarily mean service health has recovered.

These are actual backend bugs. Logs expose evidence IDs, stack traces where applicable, source locations, and the service version for investigation.

The log search supports a Datadog-style API subset: AND-combined field:value terms, @attribute:value filters, time ranges, and cursor pagination. Unsupported OR expressions, groups, and range expressions return HTTP 400.
Follow a request through its evidence
For a downstream AI workflow: identify the repository and service mapping, inspect the implicated code, write a report or propose a PR, then restart the service, reset the demo, and rerun each scenario to verify the fix. An isolated fixed copy was validated as healthy for all three bug scenarios.
The endpoints provide evidence for a downstream AI report or pull-request workflow. Automated report generation and PR creation are not built into this sandbox.
Availability and handoff notes
These are temporary demo URLs. They can change after a tunnel restart. Keep the host Mac awake while using the demo; the application and tunnels run on that machine.
Copy a fresh invitation after a restart if the URL changes. Use the live task journal to follow work as it happens.
The invitation token is kept in page memory and the invitation fragment; it is not saved in localStorage. Opening a demo link establishes an HttpOnly browser session on that demo origin, then removes the credential from the destination address.
